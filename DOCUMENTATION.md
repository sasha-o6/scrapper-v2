# Технічне завдання: Багатокористувацька система моніторингу Telegram-каналів (Userbot + TMA)

## 1. Суть проєкту
Розробка багатокористувацької, стійкої до блокувань системи моніторингу Telegram-каналів (Userbot-скрапер) із керуванням через безпечний інтерфейс Telegram Mini App (TMA). 

Система дозволяє користувачам авторизувати власні акаунти Telegram (через MTProto), налаштовувати цільові канали для прослуховування та задавати складні критерії фільтрації повідомлень (ключові слова, додаткові умови для точного пошуку, бан-слова). Відфільтровані повідомлення проходять через санітарію тексту та персистентну чергу, після чого автоматично пересилаються у вказаний користувачем чат. Головний фокус архітектури — безпека даних (ізоляція налаштувань по `telegram_id` через валідацію `initData`), уникнення лімітів Telegram API (`FloodWait`) та мінімальне споживання ресурсів завдяки легковаговим технологіям у Docker-середовищі.

---

## 2. Основний стек технологій
* **Runtime / Backend:** Bun, Hono (для API та роутингу).
* **Telegram Core:** `mtcute` (для Userbot та клієнтської частини).
* **Database:** PostgreSQL + Prisma ORM.
* **Frontend (TMA):** Preact (`preactjs.com`) + Vite.
* **DevOps / Deployment:** Docker, `docker-compose`.

---

## 3. Архітектурні стандарти та стиль коду (ОБОВ'ЯЗКОВО до виконання)
* **Core:** Принцип єдиної відповідальності (SRP). Жодного мертвого коду. Чисті функції.
* **TypeScript:** `strict: true`. Інтерфейси мають префікс `I`, типи — префікс `T`. Використовуй `import type`. Юніони для варіантів.
* **Naming:** PascalCase для компонентів та типів, camelCase для змінних, ALL_CAPS для констант. Обробники подій: `onClick`, `setX`.
* **Preact:** Деструктуризація props. Вся логіка виноситься в кастомні хуки. Обов'язкове мемоїзування важких обчислень та колбеків (`useMemo`, `useCallback`, `memo`). Динамічні імпорти (`dynamic()`) за замовчуванням. Використання Skeleton loaders.
* **Styling:** Desktop-first підхід (breakpoints від `max-2xl` до `xxs`). Tailwind + SCSS modules. Утиліта `cn()` на базі `clsx` + `tailwind-merge`.
* **Animations:** Жодних сторонніх бібліотек (без motion). Анімувати виключно `transform` та `opacity` засобами чистого CSS. Ніяких layout/paint властивостей. Використовувати `will-change`.

## 4. Поля для налаштування (Інтерфейс TMA)
Кожен користувач керує власним ізольованим середовищем через UI. Доступні наступні поля та елементи керування:

### Маршрутизація та Стан
* **Цільовий чат (Target Chat):** Поле вводу ID або username (`@chat`), куди система пересилає відфільтровані повідомлення.
* **Глобальний статус (Active/Pause):** Перемикач для тимчасової зупинки моніторингу без видалення конфігурації чи розлогіну.

### Джерела даних
* **Список каналів:** Інтерфейс (CRUD) для додавання публічних посилань (`t.me/channel`) або числових ID приватних каналів.

### Критерії фільтрації
* **Ключові слова:** Список базових тригерів (логіка «АБО»).
* **Перемикач «Точніший пошук» (Strict Mode):** Білевий тогл (Увімкнено/Вимкнено).
* **Додаткові слова:** Список, активний лише при увімкненому «Точнішому пошуку» (логіка «І» — має бути ключове + додаткове).
* **Бан-слова:** Абсолютний блокувальник. Збіг з цим списком миттєво відхиляє повідомлення.

### Робота з історією
* **Глибина парсингу:** Поле для вводу кількості днів (X) для збору історичних даних.
* **Кнопка «Зібрати історію»:** Тригер запуску фонового парсингу ретроспективи.

## 5. Структура системи та Бізнес-логіка

### 5.1. Database (Prisma + PostgreSQL) - Multi-tenant
Усі дані повинні бути жорстко прив'язані до `telegram_id` користувача.
* **User:** Основна таблиця (`telegram_id`).
* **Session:** Custom storage adapter для збереження стрінг-сесії `mtcute` безпосередньо в БД (без локальних файлів).
* **Config:** Зберігання всіх полів налаштувань (канали, списки слів, цільовий чат, статус).
* **MessageQueue:** Персистентна черга відправки (`id`, `user_id`, `message_text`, `status`: `PENDING` | `SENT` | `FAILED`, `target_chat`).
* **ProcessedMessage:** Таблиця для дедуплікації (`channel_id`, `message_id`).

### 5.2. Security & Mini App API (Hono)
* **Auth Middleware:** Маршрути Hono API захищаються middleware, який валідує криптографічний підпис `initData` від Telegram.
* Доступ до бази даних та черги виконується виключно з фільтрацією по `user_id`, отриманому з валідного `initData`.

### 5.3. Userbot Service (`mtcute`) & Auth Flow
* **TMA Auth Flow:** Реалізувати покрокову авторизацію в MTProto через Mini App (Введення телефону -> Код з Telegram -> 2FA пароль).
* **Real-time Listener:** Підписка на події `newMessage`.
* **Historical Fetcher:** Жорстка пагінація з паузами (`sleep`) між запитами до Telegram API.
* **Логіка фільтрів:** Збіг з ключовими -> перевірка додаткових (якщо треба) -> перевірка бан-слів.

### 5.4. Persistent Message Queue (Черга відправки)
Фоновий воркер, який кожні 3-5 секунд бере один запис зі статусом `PENDING` з `MessageQueue`, відправляє його у цільовий чат і змінює статус на `SENT`. Жодних in-memory масивів.

### 5.5. Formatter & Escaper
Чиста функція форматування (HTML або MarkdownV2) з обов'язковим ескейпінгом оригінального тексту (`msg.message`).

Шаблон виводу:
```typescript
`**Канал/чат:** ${msg.channelTitle ?? channel}\n` +
`**Дата:** ${new Date(msg.date * 1000).toLocaleString()}\n` +
`**Повідомлення:**\n\n` +
escapedMessageText +
`\n\n\n` +
`**Ключові слова:** \n` +
msg.keyWords[0].join(', ') +
'   ___   ' +
(msg.keyWords[1]?.join(', ') || '') +
`\n` +

## 6. Детальний план виконання (Ітеративна розробка)

**Увага агенту:** Розробка ведеться строго за наведеними етапами. Кожен крок має бути завершений, покритий базовими перевірками та готовий до ізольованого тестування перед переходом до наступного. Уникай написання коду "наперед".

### Етап 1: Інфраструктура бази даних та бекенду
1. Ініціалізувати проєкт за допомогою Bun (`bun init`).
2. Налаштувати Prisma ORM. Створити схему `schema.prisma` із моделями: `User`, `Session`, `Config`, `MessageQueue`, `ProcessedMessage`.
3. Згенерувати міграції та перевірити підключення до локального PostgreSQL.
4. Налаштувати базовий логер для бекенду (можна використати вбудований `console` з форматуванням або легку бібліотеку).

### Етап 2: Безпека та Hono API
1. Підняти базовий сервер Hono.
2. Реалізувати криптографічний Middleware для перевірки `initData` від Telegram Mini App. Middleware повинен валідувати підпис (HMAC-SHA-256) за допомогою токена бота і витягувати `user_id`.
3. Створити захищені REST-ендпоінти (CRUD) для таблиці `Config`: оновлення цільового чату, керування списками каналів та слів, перемикання статусів.

### Етап 3: Інтеграція Userbot (`mtcute`) та Авторизація
1. Написати `CustomStorageAdapter` для `mtcute`. Сесії (auth keys, збережені контакти/піри) повинні писатися/читатися виключно з таблиці `Session` у PostgreSQL. Жодних `.session` файлів на диску.
2. Створити Hono-ендпоінти для процесу логіну:
   - `POST /auth/send-code` (отримати код на номер телефону).
   - `POST /auth/sign-in` (відправити код підтвердження).
   - `POST /auth/check-password` (якщо увімкнено 2FA).
3. Написати `ClientManager` — клас/сервіс, який тримає в пам'яті активні інстанси `TelegramClient` для всіх авторизованих користувачів та відновлює їх при рестарті сервера.

### Етап 4: Логіка скрапінгу та Черга
1. Додати підписку на події `Dispatcher.on('newMessage')` в інстанси клієнтів.
2. Написати чисту функцію фільтрації повідомлень: перевірка на бан-слова (пріоритет), перевірка ключових слів (АБО), перевірка додаткових слів (І, якщо увімкнено Strict Mode).
3. Створити функцію Historical Fetcher з циклом `while` і `offset_date`. Обов'язково додати затримку `await sleep(2000)` між батчами для уникнення `FloodWait`.
4. Реалізувати Background Worker для таблиці `MessageQueue`. Воркер повинен прокидатися кожні 3-5 секунд, брати один запис зі статусом `PENDING`, форматувати текст (із ескейпінгом) і відправляти в цільовий чат.

### Етап 5: Telegram Mini App (Frontend)
1. Ініціалізувати клієнтську частину на Preact + Vite + TailwindCSS. Налаштувати alias-и та SCSS modules.
2. Інтегрувати Telegram Web Apps Script (`telegram-web-app.js`) та створити хук `useInitData`.
3. Зверстати екран авторизації (введення телефону, коду, пароля) зі скелетонами під час завантаження.
4. Зверстати дашборд:
   - Блок налаштувань (Цільовий чат, Статус моніторингу).
   - Керування масивами (Канали, Ключові слова, Додаткові слова, Бан-слова) з можливістю додавання/видалення елементів.
   - Секція збору історії (Інпут кількості днів + кнопка запуску).

### Етап 6: Dockerization
1. Написати двохетапний `Dockerfile` для бекенду (Bun + Hono).
2. Написати процес збірки для Preact (Vite build) і налаштувати Hono на роздачу статики з папки `dist` фронтенду (або налаштувати Nginx в окремому контейнері, якщо АІ вважає це більш доцільним).
3. Створити `docker-compose.yml`, який об'єднує БД (PostgreSQL) та додаток. Забезпечити правильну послідовність запуску (`depends_on`).
